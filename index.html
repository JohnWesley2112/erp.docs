1. Project Overview & Technology Stack

Systra is a school ERP under active development. The frontend is a React 19, TypeScript, Vite SPA using Material UI, Redux Toolkit, Axios, and React Router. The backend is a TypeScript / Express 5 API using Prisma 6 and PostgreSQL. Source includes academic structure, student/enrollment, teacher/assignment, attendance, user, and permission workflows.

The backend separates a central admin database for identities, memberships, tenant records, database configuration, and refresh sessions from per-tenant databases for school profiles, academics, attendance, roles, and permissions. Tenant-aware middleware resolves a tenant before domain routes use its Prisma client. This describes source architecture, not a verified deployment.

Authorization

Tenant-local role and permission codes are checked by API middleware; frontend route guards are a usability layer, not the security boundary.

School Modules

School features are divided into API modules, with routes, controllers, and services, alongside frontend pages and API helpers.

Relational Integrity

Prisma foreign keys protect relationships within each database; cross-database identity IDs are logical references checked in application code.

Separate Tiers

The SPA and API are separate codebases. Deployment workflows exist in source, but successful deployment and live infrastructure are not verified here.

Implementation and verification status

Multi-tenancy and school-domain functionality are present in source. Builds, migrations, tests, deployed endpoints, and end-to-end workflows have not been verified for this documentation update; do not infer production readiness.

Package manifests declare React 19, TypeScript 5.9, Vite 8, MUI 9, Redux Toolkit, React Router 7, and Axios for the web app; Express 5, Prisma 6, bcrypt, JWT, Swagger UI, Vitest, and Supertest for the API. Dependency declarations do not establish successful builds or tests.

3. Database Architecture & Relationships

The admin Prisma client uses prisma/admin/schema.prisma and ADMIN_DATABASE_URL. The tenant Prisma client uses prisma/tenant/schema.prisma and connects dynamically from tenant database configuration. Migrations are configured under prisma/admin/migrations and prisma/tenant/migrations; the separate prisma/schemas files are not selected by current configs.

Database / domainModels and relationships
Admin databaseUser, Tenant, UserTenantMembership, TenantDatabaseConfig, RefreshSession, and RefreshSessionToken. Membership/user and tenant/config/session links are Prisma foreign keys; refresh tokens reference sessions and rotation history.
Tenant: school setupInstitution, AcademicYear, Class, Section, and Subject. Sections have foreign keys to classes and academic years.
Tenant: school operationsTeacher, TeacherAssignment, Student, Guardian, StudentGuardian, Enrollment, AdmissionSerial, AttendanceSession, AttendanceRecord, and AuditLog. Domain relations use foreign keys within the tenant database.
Tenant: access controlUserProfile, Role, Permission, UserRole, and RolePermission. Assignment joins have foreign keys; RolePermission has a composite primary key.

Cross-database IDs are logical references, not foreign keys. Tenant UserProfile.userId, Teacher.userId, AttendanceSession.createdByUserId, and AuditLog.actorUserId do not relate to admin rows through Prisma. Application logic must maintain consistency.

The tenant schema also declares user, tenant, membership, and database-config models. Its tenant ID is UUID while the admin schema's Tenant.id is integer; login and tenant-directory code use the admin Prisma client. Clarify ownership and lifecycle before relying on these parallel declarations.

4. Authentication, Tenant Resolution & RBAC

Authentication and tenant resolution

  1. POST /api/v1/auth/login verifies an active admin-database user with bcrypt and returns active tenant memberships. One active tenant is selected automatically; users with multiple memberships can select one.
  2. Access JWTs last 15 minutes and contain user ID, email, optional tenant ID, and session ID. A random refresh token is hashed in the admin database and delivered in an HttpOnly, Secure cookie.
  3. The refresh endpoint rotates tokens; replay of a consumed token revokes the session. Refresh sessions last seven days; logout revokes the associated session.
  4. Protected feature routes authenticate the bearer token, validate active membership and tenant status, load tenant database configuration, then attach a tenant Prisma client.
  5. Most feature routes check a tenant-local permission before the controller. Refresh and logout additionally enforce the configured client origin.

These are source-level findings, not a security certification. Deployment cookie behavior, secret management, CSRF posture, and end-to-end session flows remain unverified.

Roles, permission codes, and assignments

The tenant seed defines INSTITUTION_ADMIN, CAMPUS_ADMIN, and TEACHER. The catalog includes institution.read, institution.manage, academic.read, academic.manage, student.read, student.create, student.update, teacher.read, teacher.create, teacher.update, user.read, user.manage, role.read, role.manage, attendance.read, attendance.mark, attendance.submit, and audit.read.

7. Current Status, Limitations & Next Steps

Source implementation; verification pending

The repository includes school modules, separate admin/tenant schemas, migration directories, seeds, and API tests. Builds, Prisma validation, migrations, and tests were not run for this update. No feature is represented as tested, deployed, or production-ready.

Limitations and open questions

  • The tenant schema declares identity-related models alongside admin models; tenant IDs are UUIDs versus integer IDs in the admin schema. Clarify ownership, seeding, and migration intent.
  • Several tenant identity IDs are logical references without cross-database foreign keys, so application-level lifecycle consistency is essential.
  • Test presence does not establish passing behavior. Tenant isolation, authorization allow/deny behavior, cookie settings, and error handling need controlled verification.

Prioritized next steps

  1. Run Prisma validation/generation, API and frontend builds, lint, and targeted auth, tenant, user, RBAC, and domain tests in non-production; record outcomes.
  2. Clarify authoritative user, membership, profile, and role ownership and define cross-database failure recovery.
  3. Add authorization allow/deny and tenant-isolation tests; reconcile role assignments with route gates and teacher section scope.
  4. Review validation, refresh-cookie and origin/CSRF configuration, login throttling, secret handling, and audit coverage before production use.
  5. Verify migration/seed procedures, backups, health checks, and API contracts in non-production infrastructure.

8. CI/CD & Deployment Evidence

GitHub Actions deployment workflows exist in both repositories and define DigitalOcean-host deployment steps. Their presence does not prove a successful run, active host, live production routing, or service health.

Web workflow (source)

Push to main; Node 20; install and build; SCP to /var/www/web.erp; set permissions; run nginx -t and reload Nginx.

API workflow (source)

Push to main; Node 22; build with database URL secrets; SCP to /root/api.erp; install production dependencies; generate both Prisma clients; restart and save PM2 process state.

A local Nginx configuration is present in the repository. Production domains, deployment outcomes, and active server state were not independently verified.
